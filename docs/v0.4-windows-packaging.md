# v0.4 · Windows x64 便携版（设计与审计）

目标：让普通 Windows 用户**不装 Python、不开终端、不配环境变量**就能用它完成第一篇
Obsidian 笔记。形态是**便携 ZIP**（不是安装器）—— 解压到哪就在哪，不写注册表、
不装系统服务、不建开始菜单项，删掉目录就等于卸载。

配套阅读：[v0.4-macos-packaging.md](v0.4-macos-packaging.md)（同一套思路的 macOS 版）。

## 一、审计结果（先查再写码）

| # | 审计项 | 结论 |
|---|---|---|
| 1 | Python 版本要求 | `requires-python = ">=3.11"`；内嵌 **3.13.15** |
| 2 | FastAPI 启动方式 | `backend/scripts/serve.py`（argparse + uvicorn） |
| 3 | 配置机制 | `.env` + pydantic-settings，共 18 个键 |
| 4 | 数据库路径 | 默认 `sqlite:///./data/knowledgeflow.db` —— **相对 cwd**，打包层改喂绝对路径 |
| 5 | ASR / OCR | faster-whisper（+ ctranslate2 / onnxruntime / av）+ pytesseract；**OCR 的真引擎是系统 tesseract** |
| 6 | 音视频解码 | 走 PyAV，**不调用 ffmpeg CLI** → 「系统没装 ffmpeg」不该拦人 |
| 7 | 测试 | pytest，离线（Mock LLM / MockTransport） |
| 8 | 打包层要不要动业务代码 | **不要**。这是本次最重要的约束，实测也确实一行没动 `backend/app/` |

### 审计推翻了「直接照抄 macOS 版」这个假设

macOS 那套是「内嵌解释器 + 原样后端」，思路可以照搬，但**系统调用层几乎每一项都要重写**：

| 能力 | macOS 写法 | Windows 上为什么不能照抄 |
|---|---|---|
| 判断进程是否活着 | `os.kill(pid, 0)` | **在 Windows 上它会真的把进程杀掉**（`os.kill` 走 `TerminateProcess`）。改用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess`，只读退出码 |
| 结束整棵进程树 | `os.killpg` / `SIGTERM` | Windows 没有信号与进程组。用 `taskkill /PID <pid> /T /F` |
| 找「谁在占端口」 | `lsof -i :port` | 用 `netstat -ano -p TCP` 解析，再用 `OpenProcess` 校验 |
| 配置文件权限 | `chmod 0600` | 没有 POSIX 权限位。用 `icacls`：`/inheritance:r /grant:r "<user>:(F)"`，**并且要摘掉从上级目录继承来的 `Users` / `Everyone`** —— 否则同一台机器上别的账号能读到 API Key |
| 用户数据目录 | `~/Library/Application Support` | `Path.home()` 在 Windows 上**忽略 `HOME`**，读 `USERPROFILE`；而正统答案其实是 `LOCALAPPDATA`（可能被组策略指到别的盘）。三级回退，优先 `LOCALAPPDATA` |
| 后台起子进程 | `start_new_session=True` | 用 `CREATE_NO_WINDOW`，否则会闪一个黑色控制台窗口 |
| 弹向导 | `osascript` | 用 **tkinter**（标准库自带，不引第三方 GUI 依赖） |
| 静默启动 | `LSUIElement` | 无对应物；改为「不显示控制窗口」的 `--no-window` |

### 后端本身的三处平台假设（本次一并修掉）

后端是纯 Python，但有 3 个地方默默假定了 POSIX。**这些是真正的跨平台缺陷，
修在业务代码里**（与「打包层不动业务代码」不冲突 —— 那是打包，这是修 bug）：

1. **Obsidian 库内路径用 `os.path.join` 拼**。Windows 上会拼出 `a\b\c.md` 写进
   frontmatter 和 `[[wikilink]]`，而 Obsidian 的链接语法是正斜杠 —— 在 Mac 上打开
   这份笔记会全是断链。改成 `posixpath.join`：**vault 内部的路径是 Obsidian 的
   命名空间，不是操作系统的路径**，这件事跟跑在哪个系统上无关。
2. **`demo_pipeline.py` 打印路径用 `str(path)`**，Windows 上输出反斜杠。改成 `as_posix()`。
3. **测试用 `symlink` 造场景，却不检查平台能不能建**。Windows 建符号链接需要
   开发者模式或管理员权限（WinError 1314）。加 `symlink_problem()` 探测 +
   `requires_symlinks` 标记，建不了就明确跳过，而不是报一堆假失败。

## 二、架构

```
KnowledgeFlow-0.4.0-windows-x64/          ← 解压到哪就在哪
├── KnowledgeFlow.exe                     ← 双击入口（PyInstaller --onefile --noconsole）
├── KnowledgeFlow.cmd                     ← 命令行入口（走内嵌解释器）
├── runtime/                              ← 内嵌 Python 3.13.15 + 全部依赖
├── backend/                              ← **原样的后端代码**（无 .env / 无 data / 无 tests）
├── launcher/kf_app/                      ← 启动器（本目录上层的 packaging/windows/launcher）
└── packaging/                            ← 依赖清单，排障时对照
```

数据与程序**严格分离**：

```
%LOCALAPPDATA%\KnowledgeFlow\
├── config\settings.json      ACL 仅当前用户，含 API Key
├── data\knowledgeflow.db     + media\
├── logs\app.log, launcher.log
├── cache\huggingface\        Whisper 模型落这里，不污染用户 profile
└── runtime\service.json      进程状态（辅助信息，不作为判定依据）
```

**为什么数据不能放解压目录**：便携包会被拷到 U 盘、被挪到别处、被整个删掉重下一份。
数据库写在里面的话，用户「重新解压一份」就等于丢数据；而且放在 `C:\Program Files`
之类的位置，普通用户根本没有写权限。

### 为什么双击入口是 exe，而不是一个 .cmd

`.cmd` 双击会留一个黑色控制台窗口，**而关掉那个窗口会连带杀掉后端** ——
用户会以为「程序自己退了」，这是个很难查的观感 bug。所以双击入口用 PyInstaller
冻一个 `--noconsole` 的 exe（代价是包里多一个自带解释器的 exe，只用来跑启动器；
后端仍然用 `runtime\` 里那份）。

但**无控制台的 exe 里 `print()` 没有出口**，而 `--status` / `--stop` / `--check`
本来就是给人看输出的。所以命令行另给一份 `KnowledgeFlow.cmd`，走内嵌解释器。
不用 `.vbs`：那玩意儿会被安全软件重点关照，观感也不像正规软件。

## 三、启动器（`packaging/windows/launcher/kf_app/`）

| 模块 | 职责 |
|---|---|
| `paths.py` | 从 exe 位置推出全部路径；安装目录**要求同时存在** `runtime\python.exe` 与 `backend\scripts\serve.py` 两个标记 |
| `settings.py` | `settings.json` ↔ 后端 18 个环境变量；`probe_llm` / `probe_vault`；`icacls` 收紧 ACL |
| `service.py` | 启动 / 探活 / 复用 / 关闭；单实例；孤儿处理 |
| `wizard.py` | 首次向导（tkinter）+ 环境检查 + `KF_SETUP_NONINTERACTIVE` 非交互模式 |
| `control.py` | 一个可见的小控制窗口（状态 + 打开界面 + 停止服务），600ms 轮询 |
| `main.py` | 入口、子命令、信号处理 |

关键设计：

- **PyInstaller 冻结后 `__file__` 不可用**：它指向临时解包目录
  （`sys._MEIPASS`，形如 `C:\Users\x\AppData\Local\Temp\_MEI12345\`）。从那里往上找
  永远找不到安装目录，于是会**静默退化成「开发模式」** —— 表现为「打包好的 exe
  找不到自己的 backend」。所以冻结时必须用 `sys.executable`。
  冒烟测试专门有一条守这个：跑打包好的 exe，检查输出里有没有「内置运行环境 /
  后端程序 / 已就绪」。
- **判定「是否已在运行」只信 `/api/health`，不信 pid 文件。** 用户强杀启动器后
  后端可能还活着，pid 文件已无意义。而且探活还要**确认那个健康响应是自己人**：
  同一个端口上可能坐着别的服务（本项目自己的测试就撞过），所以要比对版本 / 身份字段。
- **`--stop` 找不到状态文件时用 `netstat` 找监听者**，`taskkill /T` 收掉整棵树，
  杀完**复查端口确实释放**才敢说「已停止」。
- **失败一律翻译成人话**：不弹 traceback，只给「XX 缺失 / 请检查 YY」+ 日志路径。
  `--check` 在任何情况下都不许打出 traceback（有测试钉住）。
- **输出按控制台编码降级，并且无条件留一份 `console.log`。**
  中文 Windows 的控制台是 GBK，`✓`（U+2713）不在码表里 —— `print("✓ …")` 抛
  `UnicodeEncodeError`，把 `--check` 这条**纯诊断**命令变成 traceback：
  退出码 1、stdout 一个字节都没有，用户唯一的线索是一行
  `'gbk' codec can't encode character '\u2713'`。所以：
  标记按 `sys.stdout.encoding` 挑（GBK 上显示 `[OK]` / `[--]`，UTF-8 上仍是 `✓` / `✗`，
  见 `wizard.console_marks`），流本身设成 `errors="replace"`，
  并且 `stdout` / `stderr` 都 tee 一份 UTF-8 的 `console.log`。
- **`console.log` 必须无条件写**，不能只在 `sys.stdout is None` 时接管。
  双击启动时 `sys.stdout` 确实是 `None`（那种情况下用户**看不到任何输出**，
  日志是唯一线索）；但从 cmd / PowerShell 启动时它会**继承控制台句柄**，
  是一个既不是 `None`、也按 ANSI 码页重开的真流 —— 靠 `is None` 判断等于
  **默认**「输出有人看得见」，而最需要日志的那一次恰恰是没人看得见的那一次。
- **服务永远只绑回环。** 后端没有鉴权，绑到 `0.0.0.0` 等于把「写你 Obsidian 库、
  用你 LLM 额度」的接口开放给局域网。`test_service_start_never_exposes_lan`
  用注入的进程工厂抓真实 argv 来守它。

## 四、构建（`scripts/build_windows_x64.ps1`）

```powershell
.\scripts\build_windows_x64.ps1            # 完整构建（含 ASR/OCR）
.\scripts\build_windows_x64.ps1 -Minimal   # 不带 ASR/OCR，包更小
.\scripts\build_windows_x64.ps1 -NoZip     # 只出目录，不打 ZIP
.\scripts\build_windows_x64.ps1 -Clean     # 先清 build\ 再构建
```

八步：**环境检查 → 清理 → 取内嵌 runtime → 装核心依赖 → 装可选 ASR/OCR →
组装目录树 → 生成图标与 exe → 冒烟测试 → 打 ZIP**。

内嵌 runtime 用 **python-build-standalone**（可重定位），与 macOS 版**同一个 tag
（`20260929`）、同一个 Python 版本（3.13.15）** —— 免得「同一个项目在 Mac 上
3.13.15、在 Windows 上 3.13.9」这种没必要的差异。有测试比对两个平台的构建脚本，
钉住这两个常量。

### 这份脚本踩过的坑（每条都是实测出来的）

**1. `.ps1` 必须以 UTF-8 *带 BOM* 保存。**
Windows PowerShell 5.1 读 `.ps1` 时，没有 BOM 就按系统 ANSI 码页解（中文机器上是
GBK）—— 脚本里全是中文注释，解错之后某些多字节序列会把后面的引号「吃掉」，
于是 PowerShell 报的是一堆莫名其妙的语法错误（实测：「表达式或语句中包含意外的
标记 `"stage'`」「此语言版本中不支持 `"from` 关键字」），**而真正的原因（编码）
一个字都不提**。有测试守着这条。

**2. `$IsWindows` 在 5.1 上不存在。**
它是 PowerShell 6+ 才有的自动变量，而脚本开头有 `Set-StrictMode -Version Latest`
—— 读未定义的变量直接是终止性错误，脚本还没开始干活就死了。先用版本号短路：
`if ($PSVersionTable.PSVersion.Major -ge 6 -and -not $IsWindows)`，5.1 上右边根本不会被求值。

**3. 原生程序往 stderr 写一行就会打断脚本。**
`$ErrorActionPreference = 'Stop'` 下，PowerShell 会把原生程序的 stderr 包装成
`NativeCommandError` 当场终止 —— **哪怕它退出码是 0**。而这类输出是家常便饭：
curl 的下载进度条、pip 的弃用警告、robocopy 的统计。实测就是 curl 的进度条把
「2/8 准备内嵌 Python runtime」打断的，报出来还是个 `RemoteException`，
完全指不到「EAP 太严」这个真因。所以包一层 `Invoke-Native`：临时把 EAP 放回
`Continue`，**用退出码判断成败**。

**4. 「数组 `-ne 0`」是过滤语义，不是比较。**
`$code = Invoke-Pip ...` 如果连 pip 的输出一起捕获，`$code` 就变成
`@(几十行输出…, 退出码)`；而 PowerShell 里 `数组 -ne 0` 返回的是**所有不等于 0
的元素**，非空数组恒为真 —— 于是**每一次安装都被判成失败**。修法：输出走
`Out-Host`，函数只返回 `$LASTEXITCODE`。

**5. `Get-Command curl` 永远成功。**
在 PowerShell 5.1 里 `curl` 是**别名**，指向 `Invoke-WebRequest`。所以
「缺工具就早退」这个检查成了摆设，真到下载那一步才炸（而那时已经跑了好几分钟）。
必须写 `curl.exe` / `tar.exe` / `robocopy.exe`。

**6. `Remove-Item -Recurse` 会留下半棵残树。**
两个毛病：路径超过 260 字符直接报「路径太长」并停下；遇到只读文件抛
`UnauthorizedAccessException` 也停下（`tar.exe` 是按归档里的权限位落盘的）。
而**残树比慢更危险** —— 它会污染下一轮构建。改用 `Remove-Tree`（.NET API）：
给 `Directory.Delete` 传 `\\?\` 前缀绕开 MAX_PATH；**先直接删，只在被只读文件挡住时
（`catch UnauthorizedAccessException`）才去摘只读属性**（反过来写等于把上万个文件
多遍历一次，而 `build\runtime` 有一万多个文件）。

**7. `PYTHONPATH` 会被子进程继承，插进内嵌解释器的 `sys.path`。**
构建机上只要设了它，路径上任何 `sitecustomize.py` 都会被**自动执行**；
更糟的是 PyInstaller 的分析可能把不相干的模块打进交付给用户的 exe。
**这不是假想问题**：本项目自己的构建机上就带着一个（指向 IDE 的垫片），
它让构建工具 venv 的 `ensurepip` 退出 1 —— 而报错只说「ensurepip 返回非零」，
一个字都没提 `PYTHONPATH`。
所以脚本开头清掉 `PYTHONPATH` / `PYTHONHOME` / `PYTHONSTARTUP` / `PYTHONEXECUTABLE`
并设 `PYTHONNOUSERSITE=1`（用户级 site-packages 会**遮蔽**内嵌 runtime 里那份）。
**同样的处理也补进了两个平台的启动器 `build_env()`** —— 用户机器上同理。

**8. venv 的判据是「pip 能用」，不是「python.exe 在」。**
`python -m venv` 是分步建的：目录与 `Scripts\python.exe` 先落盘，`ensurepip` 在后面。
ensurepip 失败时**目录已经存在** —— 只看 python.exe 会把半成品当成品，
下次构建跳过创建，然后在 `$ToolsPy -m pip install` 那里报一个跟真实原因
（venv 没建成）毫不相干的错。

**9. 冒烟测试必须用打包好的产物真的跑一次。**
而且要把 `%LOCALAPPDATA%` 指到临时目录（并在 `finally` 里恢复）—— 否则每构建一次，
构建机的真实 `%LOCALAPPDATA%\KnowledgeFlow` 就被写一遍，而那里有 `settings.json`
（内含 API Key）。

**10. 冒烟测试要模拟「用户的机器」，不是「构建机」。**
构建机上常设 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`（本脚本第 0 步自己就设了
后者），而这两个变量会让内嵌解释器绕过 GBK 输出问题 —— 于是
「中文 Windows 上 `--check` 抛 `UnicodeEncodeError`」这个**真实缺陷**
在构建机上永远测不出来。实测正是这样漏过去的：exe 在用户的 GBK 控制台上
退出码 1、stdout 一个字节都没有，而这里的冒烟测试却「通过」了。
所以第 7 步临时清掉这两个变量（`finally` 里恢复），并且**必须捕获 exe 的输出
去断言** —— 只看退出码时，「找不到自己的安装目录」和「编码炸了」都表现为
退出码 1，报错时给不出任何线索。三条守卫钉住它：
`test_build_script_smoke_test_looks_like_a_user_machine`、
`test_build_script_smoke_test_captures_and_asserts_the_exe_output`、
`test_build_script_smoke_test_isolates_the_user_data_dir`。

## 五、取舍记录

- **ASR / OCR 随包内置**，但**装失败只降级**、不中断构建。构建信息按**真实结果**
  记账：说「已包含」就必须能 `import` 验过（`faster_whisper` / `av` / `pytesseract` /
  `PIL` 四个都复核一遍）—— 早期 macOS 版只看命令行开关，导致 BUILD-INFO 写
  「已包含」而包里根本没有，已修。
- **不做代码签名**。没有证书就不假装有：首次运行可能被 SmartScreen 拦一下，
  README 写清「更多信息 → 仍要运行」，**不要求用户关闭系统安全功能**。
- **只出 x64**。Windows on ARM 上 x64 二进制能靠模拟跑，但那是「能跑」不是
  「支持」；不做没验过的承诺。
- **便携版不做开机自启**。macOS 版有 LaunchAgent，Windows 版刻意不做 ——
  便携包不写注册表、不装服务，`--no-window` 留给用户自己放进「启动」文件夹。
- **构建工具装在独立 venv**（`build\.tools`），不污染内嵌 runtime ——
  否则 PyInstaller 自己会被打进包里，用户拿到一个和他的应用毫无关系的巨大 exe。

## 六、怎么验它

`backend/tests/test_windows_packaging.py`（80 项，其中平台相关的用例在非 Windows 上跳过）。
分四层：

| 层 | 代表用例 | 守什么 |
|---|---|---|
| **逻辑层** | `test_env_uses_absolute_posix_paths_for_database_and_media` | 喂给后端的 `DATABASE_URL` 是绝对路径且**没有反斜杠**（SQLite URL 里反斜杠是转义字符） |
| | `test_env_strips_inherited_python_variables` | `PYTHONPATH` 等不会被后端继承 |
| | `test_health_rejects_a_different_service_on_the_same_port` | 端口上坐着别的服务时不许误判成「已在运行」 |
| | `test_pid_alive_never_kills_the_process_it_probes` | 探活 5 次之后目标进程**还活着**（`os.kill(pid, 0)` 那个坑） |
| **输出编码** | `test_console_marks_fall_back_when_the_encoding_cannot_hold_them` | 标记按编码挑：GBK / cp1252 / 不存在的编码名都要退回 `[OK]` |
| | `test_environment_summary_is_printable_on_a_gbk_console` | 汇总文字在 GBK 上**能编码**（摘掉修复即复现 `'\u2713'` 那个错） |
| | `test_launcher_survives_a_gbk_console` | GBK 流上 `print` 不抛异常，且中文不跟着一起丢 |
| | `test_launcher_always_writes_a_console_log` | 有控制台时也照样留一份 `console.log` |
| | `test_launcher_takes_over_the_streams_when_there_is_no_console` | `stdout` 为 `None`（双击）时 `print` 不抛 `AttributeError` |
| **ACL 层** | `test_save_tightens_the_settings_acl` | 当前用户有 `(F)`，且**没有继承来的 `(I)` 条目**，没有 `Users` / `Everyone` |
| **端到端** | `test_end_to_end_start_serve_status_stop_and_reuse` | 真子进程：start → `/api/health` 200 → `/` 200 → 数据落临时目录且**仓库 data/ 未被碰** → 第二次启动报「已经在运行」 → `--status` → `--stop` → 端口释放 → 重启复用同一 DB |
| | `test_check_never_prints_a_traceback` | 启动器真子进程跑 `--check`：退出码 0、没有 traceback、中文按**管道真实编码**解得出来 |
| **构建脚本守卫** | `test_build_script_never_calls_remove_item`、`test_build_script_clears_inherited_python_env`、`test_build_script_is_utf8_with_bom`、`test_build_script_only_targets_x64`、`test_build_script_checks_tools_by_exe_name`、`test_build_script_smoke_test_looks_like_a_user_machine`、`test_build_script_smoke_test_captures_and_asserts_the_exe_output` | 上面「踩过的坑」每一条都有对应用例，防止被「优化」掉 |

**端到端那两条测试自己也要防一个坑**：它们跑的是真子进程，stdout 是**管道** ——
中文 Windows 上按 GBK 写。所以断言必须用 `_decode_console`（先 UTF-8 后退 GBK），
只按 UTF-8 解会得到乱码，报出来是「中文断言失败」而不是真正的原因。
而且 `_launcher_env` 必须**清掉** `PYTHONIOENCODING` / `PYTHONUTF8` ——
否则构建机上顺手设的 `utf-8` 会把整个缺陷盖掉（第 7 步的教训，见「踩过的坑」第 10 条）。
这条纪律值得单独记一笔：**测试环境要像用户的机器，不然测试只是在测构建机。**

`test_launcher_imports_only_stdlib_and_itself` 用 AST 解析启动器的 import：
**启动器不许 import 第三方库** —— 它要在 PyInstaller 冻结后跑，多一个依赖就多一处
「本机能跑、用户机器上炸」。

## 七、已知限制

1. **未做代码签名**：首次运行需要「更多信息 → 仍要运行」放行一次。
2. **`-Minimal` 构建不含 ASR/OCR**：界面会如实显示未启用。
3. **OCR 依赖系统 tesseract**：未安装时自动停用（既有设计，非本次引入）。
4. **ASR 首次使用需联网下载模型**（约 500 MB，落在 `cache\huggingface\`）。
5. **向导的 GUI 路径只能人工验一次**：tkinter 对话框不能用脚本点。
   逻辑路径（`KF_SETUP_NONINTERACTIVE`）有端到端测试覆盖。
6. **构建期依赖外网**（GitHub + PyPI）。国内网络需要 `KF_PIP_INDEX_URL` 指向镜像。
7. **Windows on ARM / 32 位 Windows 不支持**（见「取舍记录」）。
8. **GBK 控制台上，编码装不下的字符会显示成 `?`**（流设了 `errors="replace"`）。
   标记已经按编码挑过（GBK 上是 `[OK]` / `[--]`），所以正常输出里看不到 `?`；
   但 `logs\console.log` 里始终是完整的 UTF-8 —— 排障请看那份日志。
